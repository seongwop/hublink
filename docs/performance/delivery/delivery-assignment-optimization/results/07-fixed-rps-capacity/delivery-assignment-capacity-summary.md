# 배송 생성 고정 RPS 용량 측정 결과

### 1. 테스트 목적

최종 배송 배정 구조가 실패 없이 처리할 수 있는 지속 부하와 성능 변곡점을 확인한다.

### 2. 변경 내용

코드와 인프라는 고정하고 목표 유입량만 100 RPS부터 170 RPS까지 단계적으로 높였다.

### 3. 테스트 조건

| 항목 | 값 |
| --- | --- |
| 부하 모델 | `ramping-arrival-rate` |
| 패턴 | 30초 상승 후 3분 유지 |
| 목표 | 100, 120, 140, 150, 160, 165, 170 RPS |
| 워밍업 | 5 RPS 30초 후 DB 기준선 재초기화 |

### 4. 실행 결과

| 목표 | 안정 처리량 | 실패율 | 평균 | p95 | DB CPU 평균 | 판정 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 100 RPS | 99.99 | 0% | 48.28ms | 85.95ms | 58.67% | 정상 |
| 120 RPS | 120.00 | 0% | 42.49ms | 67.34ms | 72.09% | 정상 |
| 140 RPS | 139.99 | 0% | 42.38ms | 85.27ms | 79.32% | 정상 |
| 150 RPS | 150.00 | 0% | 57.49ms | 140.13ms | 86.86% | 권장 상한 |
| 160 RPS | 160.01 | 0% | 77.98ms | 215.60ms | 91.61% | 경고 |
| 165 RPS | 165.05 | 0% | 94.02ms | 271.92ms | 92.59% | 경고 |
| 170 RPS | 170.04 | 0% | 122.31ms | 345.73ms | 95.40% | 스트레스 상한 |

### 5. 모니터링 및 해석

모든 단계에서 dropped iteration과 Hikari pending은 0이었다. 160 RPS부터 지연과 DB CPU가 함께 상승해 애플리케이션보다 PostgreSQL CPU가 먼저 한계에 접근했다.

### 6. 결론

**WARN** — 측정상 170 RPS까지 오류는 없었지만 자원 여유를 고려한 지속 부하는 150 RPS 이하로 판단한다.
