# 배송 담당자 캐시 100VU 결과

### 1. 테스트 목적

배송 요청마다 User Service에서 2,400명의 담당자를 조회하던 비용을 Hub 단위 로컬 캐시로 줄인다.

### 2. 변경 내용

- Caffeine `deliveryManagersByHub` 캐시 적용
- TTL 60초, 최대 32개 Hub
- `sync=true`로 동시 cache miss 병합

### 3. 테스트 조건

| 항목 | 값 |
| --- | --- |
| 대상 API | `POST /internal/deliveries` |
| 부하 | 최대 100VU / 8분 |
| 입력 | supplier 1개, receiver 18개, sleep 0초 |
| 사용 Hub | 서울·부산·인천 3개 |

### 4. 실행 결과

| 항목 | 캐시 전 | 캐시 후 | 변화 |
| --- | ---: | ---: | ---: |
| User 담당자 조회 | 4,144 | 24회 | -99.4% |
| User 조회 최대 RPS | 28.90 | 0.10 req/s | -99.7% |
| User CPU 최대 | 96.97% | 21.30% | -78.0% |
| User Hikari pending 최대 | 87 | 0 | 제거 |
| 성공 처리량 | 7.93 | 43.13 req/s | 5.44배 |
| 성공 응답 p95 | 2.71 | 1.80초 | -33.6% |

첫 실행은 담당자 집계 row 누락으로 20,700건 이후 `DELIVERY_004`가 발생했다. 캐시 자체의 조회 감소는 확인됐지만 전체 테스트 판정은 실패였다.

### 5. 모니터링 및 해석

캐시 적용 후 User Service CPU와 Hikari pending이 낮아졌다. 집계 row를 전체 1,500명으로 보완한 재실행에서는 38,607건이 모두 성공했다.

| 항목 | 값 |
| --- | ---: |
| HTTP TPS | 80.43 req/s |
| 실패율 | 0% |
| p95 | 1.80초 |
| cache hit ratio | 99.97% |
| User 담당자 조회 | 24회 |

배송·경로·Outbox 증가량이 성공 요청 수와 일치했고 담당자 배정은 1,500명 전체에 분산됐다.

### 6. 결론

**PASS** — 담당자 조회 병목을 제거했고, 후속 재실행에서 집계 데이터 문제까지 보완해 전체 요청 성공을 확인했다.
