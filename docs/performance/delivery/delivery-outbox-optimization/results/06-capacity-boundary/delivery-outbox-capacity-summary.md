# Outbox 최종 파이프라인 용량 측정 결과

### 1. 테스트 목적

Outbox 발행을 부하 구간 안에서 함께 처리할 때 현재 인프라의 비포화 상한을 확인한다.

### 2. 변경 내용

최종 Outbox 구현과 인프라는 고정하고 목표 유입량만 140, 150, 160 RPS로 높였다.

### 3. 테스트 조건

| 항목 | 값 |
| --- | --- |
| 부하 모델 | `ramping-arrival-rate` |
| 패턴 | 30초 상승 후 3분 유지 |
| 목표 | 140, 150, 160 RPS |
| 워밍업 | 5 RPS 30초 후 DB 재초기화 |

### 4. 실행 결과

| 항목 | 140 RPS | 150 RPS | 160 RPS |
| --- | ---: | ---: | ---: |
| 안정 처리량 | 139.98 | 148.87 | 158.97 req/s |
| 실패 / dropped | 0 / 0 | 0 / 0 | 0 / 0건 |
| 평균 응답 | 50.66ms | 570.05ms | 771.29ms |
| p95 | 108.94ms | 1.83초 | 1.97초 |
| Data VM CPU 평균 | 85.46% | 98.59% | 98.64% |
| Hikari pending 평균 | 0 | 62.89 | 80.67 |
| Outbox Published TPS | 139.74 | 148.88 | 138.76건/s |
| backlog 최대 | 14 | 1,815 | 3,382건 |

### 5. 모니터링 및 해석

140 RPS에서는 Outbox 발행량이 유입량을 따라갔다. 150 RPS부터 DB CPU와 Hikari pending이 급증했고, 160 RPS에서는 발행 처리량이 약 139건/s에서 더 늘지 않아 차이가 backlog로 누적됐다.

### 6. 결론

**WARN** — 기능상 160 RPS까지 처리했지만 비포화 상한은 140 RPS다. 현재 병목은 JVM이 아니라 PostgreSQL CPU와 connection 경합이다.
